  1. Select the indexed BrainTumorClassifier repository.
  2. Ask: “Where is the dataset split into training and validation data?”
  3. Inspect the retrieved excerpt in src/utils.py, including the dataset splitting code.
  4. Expand the result or follow its commit-specific GitHub citation.

The app retrieves source code; it does not run the classifier or generate an LLM explanation. Similarity scores are ranking signals, not confidence probabilities.

The problem

When exploring a new repository, the task you have in mind may not match its filenames or identifiers. DevPilot lets a developer search by meaning and then verify a result against the actual source.

What I built

A browser workspace with sign-in, repository selection, indexing status, and ranked search results; a FastAPI backend that enforces ownership; and a background worker that converts source files into searchable embeddings.

  1. ImportRegister a public GitHub repository.
  2. IndexA worker discovers files and creates overlapping line windows.
  3. Embed & storeCode embeddings and source references go into PostgreSQL / pgvector.
  4. Search & verifyEmbed the query, rank matches, and open the cited commit.

Decisions and tradeoffs.

Keep indexing outside the request

A separate worker and durable PostgreSQL job queue keep lengthy indexing work out of the API request. This avoids introducing another queue service at this stage, while still requiring careful job recovery and concurrency handling.

Chunk by lines, with overlap

Line windows preserve exact file and line citations and make chunking deterministic. Overlap provides context at boundaries, but fixed windows can still split a function; syntax-aware chunking is a possible next improvement.

Separate embeddings from source chunks

The data model keeps vectors apart from chunk text, allowing a future embedding-model change without rewriting the original source excerpts.

Check ownership before searching

The search service resolves the repository for the signed-in owner before embedding a query. A repository belonging to another user is treated as not found; an unindexed repository returns an explicit error.

Evidence and limits.

The recording demonstrates a successful dataset-split lookup and inspectable citations. The source includes unit and integration tests for chunking, repository access, and the search API. A manual evaluation harness checks whether relevant files appear among ranked results and computes reciprocal rank.

No retrieval-quality benchmark is published yet. One successful demo is not a measure of overall search quality. A useful next evaluation is a labeled set of questions covering exact identifiers, conceptual questions, and missing answers.

  • Public repositories only; reindexing is manual.
  • Search returns ranked chunks, not generated answers.
  • Embedding similarity can miss exact identifiers; hybrid search is planned.
  • The application runs locally with Docker; no public live service is claimed.
